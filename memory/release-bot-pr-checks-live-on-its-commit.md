# A release bot PR's checks live on its commit, and GitHub can drop some of them

`release.yaml` dispatches `quality.yaml` on the bot branch `release/bot/vX.Y.Z-<run_id>-<attempt>` and cancels the `action_required` `pull_request` run (later listed as `failure`, as expected), so the bot PR's `statusCheckRollup` stays empty for the whole cut. `gh pr checks <n>` then prints `no checks reported on the 'release/bot/vX.Y.Z-<run_id>-<attempt>' branch` (bot PR #964, v8.0.0), so watch `gh api repos/{owner}/{repo}/commits/<headRefOid>/check-runs`, where the newest run of each required name counts, as the `Wait for required status checks` step reads it. On the v10.0.0 cut (release run 42669802166) GitHub scheduled only 6 of the 10 jobs on the dispatch run and 7 on a rerun, though v8.0.0 had scheduled all 10, and each run concluded `failure` with every job it created green. `gh run rerun --job <id>` on a superseded attempt fails with `cannot be rerun`; a fresh `gh workflow run quality.yaml --ref <bot branch>` scheduled all 10, but the 45-minute wait timed out first and closed bot PR #1074. The flaky-check retry in `docs/_internal/RELEASING.md` recovered it: **Re-run failed jobs** on the release run, approve gate 1 again through `pending_deployments`, then admin-merge the new bot PR (#1076) once its 10 required checks are green. When a required check is still missing about 12 minutes into the wait, dispatch `quality.yaml` on the bot branch at once (related: [Standing authorization for autonomous end-to-end releases, both gates included](autonomous-release-authorization.md), [Release bot PR never auto-merges: perpetually pending code_quality rule](release-pr-auto-merge-deadlock.md)).
