# Exit Codes — skf-rename-skill

Every HARD HALT in the rename workflow exits with a stable code so headless automators can branch on the failure class without grepping message text. In headless mode each HALT also prints its `SKF_RENAME_SKILL_RESULT_JSON` line through the shared emitter, which derives `exit_code` from `halt_reason` through the schema's `skf-envelope.exit_codes`; this table says where each code is raised:

| Code | Meaning              | Raised by                                                                                    |
| ---- | -------------------- | -------------------------------------------------------------------------------------------- |
| 0    | success              | step 3 (a finished rename, before the step 4 health check); step 1 §8 (the `--dry-run` exit, `status: "dry-run"`) |
| 2    | input-missing / input-invalid | step 1 §4/§5 (headless missing `old_name`/`new_name` arg) → `input-missing`; step 1 §4 (headless `old_name` matches no listed skill) → `input-invalid`; step 1 §5 (headless: the new name fails kebab-case / length / same-as-old; an interactive run asks again) → `input-invalid` |
| 3    | resolution-failure   | step 1 §2 (manifest is malformed JSON) → `manifest-corrupt`; step 1 §3 (no skill SKF generated found anywhere) → `nothing-to-rename` |
| 4    | write-failure        | step 1 §1 (the run-lock, envelope, manifest or inventory helper is missing, or the pre-flight write probe finds the run folder, skills_output_folder or forge_data_folder unwritable), step 1 §2, §3, §5 and §7 (the manifest read, the skill listing, the new-name validator or the version listing prints no JSON), step 1 §4b (the run lock could not be taken), step 1 §6 and §8 (an auto-decision could not be recorded), step 2 §0 (a helper is missing) and step 2 §1 (the run lock could not be renewed) → `write-failed`; step 2 §1 (copy → `copy-failed`); step 2 §2 (inner-dir rename, file content update or the record it writes to the run folder) / §4 (symlink repair) → `write-failed`; step 2 §6 (manifest backup or write → `manifest-write-failed`). step 2 §7 (context-file rewrite) is **best-effort and never halts**: per-file failures are recorded in `context_files_failed` and the rename still succeeds (manifest + disk are canonical; re-run `[EX] Export Skill` to retry). |
| 5    | state-conflict       | step 1 §4a, entered from §3 or §4 (a folder SKF did not generate, one that also holds entries SKF did not generate, or ownership that cannot be checked, in the skill folder or its forge folder, or a forge folder that is a link, is not a folder, or cannot be listed → `not-skf-output`; a flat-layout skill → `flat-layout`); step 1 §5 (name-collision check fails: target name already in use, or `improvement-queue`, or an earlier rename to that name stopped after re-keying the export manifest, whose leftover folders the message names) → `name-collision`; step 1 §6 (source-authority="official" headless without `--acknowledge-official` or `force_source_authority_in_headless`) → `source-authority-blocked`; step 1 §4b (another rename of the same skill holds a run lock that has not gone stale) and step 2 §1 (this run's lock went stale while it waited at a step 1 gate) → `halted-for-concurrent-run`; step 2 §5 (no-trace verification failed: `{old_name}` still present inside the new location, or the verifier exits 2 with no JSON → `verify-failed`; note this rollback is code 5, unlike the copy/write rollbacks at code 4) |
| 6    | user-cancelled       | step 1 §6 (source-authority warning [N]); step 1 §8 confirmation gate `[N]`; any prompt that accepted `cancel`/`exit`/`:q` → `user-cancelled` |
