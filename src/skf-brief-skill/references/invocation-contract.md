# Invocation Contract — skf-brief-skill

Full argument set, gate map, exit codes, and headless result envelope for `skf-brief-skill`. Interactive callers can ignore this file; headless automators and pipeline integrators consult it. This is the canonical statement of the `from_brief` ratify contract, which `references/gather-intent-ratify.md` carries out for both ratify paths: a brief path given at the first interactive prompt, and a headless `from_brief`.

## Invocation Contract

| Aspect | Detail |
|--------|--------|
| **Inputs** | The headless arguments, each with its default and the halt it can raise, are the Arguments table of `references/headless-args.md`, which `skf-validate-brief-inputs.py` enforces: `target_repo` and `skill_name` are required, every other one is optional. Two of them route the run elsewhere: `from_brief` [optional: path to a pre-authored `skill-brief.yaml` to *ratify*: when supplied it is the source of truth, `target_repo`/`skill_name` become optional/derived-from-brief, and the run mirrors the interactive §3.1a ratify path: schema-validate, skip analyze-target/scope-definition, write through the canonical writer in place], `[auto]` [optional: bracket modifier passed via pipeline context: when present, BS loads the upstream brief from `brief_path` in pipeline data, enriches it with doc detection, and writes through the canonical writer; requires `brief_path` from AN's `SKF_ANALYZE_RESULT_JSON`] |
| **Gates** | step 1: Input Gate [use args] (`references/headless-args.md`) | step 1 ratify: Choice Gate [R] | step 2: Choice Gate [P] (a truncated GitHub tree), and the workspace of a monorepo [the repo root, or the workspace an `include` glob names] | step 3: Choice Gate [the `scope_type` argument, else the recommendation] | step 3: Input Gate [the `include` and `exclude` arguments, else the scope type's boundary default; a `reference-app` scope, or a `specific-modules` `scope_type` argument naming no module, halts] | step 3: Confirm Gate [C] | step 4: Confirm Gate [C] | step 5: Overwrite Gate [Y/N] (the brief exists; headless halts `overwrite-cancelled` unless `force` was supplied) |
| **Outputs** | `skill-brief.yaml` at `{forge_data_folder}/{skill-name}/skill-brief.yaml`; one `SKF_BRIEF_RESULT_JSON` line on stdout at the end of a successful run when `{headless_mode}` is true or the run is in `[auto]` mode (see Result Contract below); for the run itself, a scratch folder under `{project-root}/_bmad-output/.skf-run/` holding what it hands its helpers (the repository's file list, fetched files, JSON payloads), which the run deletes once the brief is written or the user cancels (any other halt leaves it in place, less a clone of the repository) |
| **Headless** | All gates auto-resolve with heuristic-driven or default action when `{headless_mode}` is true; step 1's input gate (`references/headless-args.md`) validates the pre-supplied inputs before any stage uses them, and the gates that would otherwise prompt consume them; absent `source_authority` and `scope_type` are resolved by signal-driven detection (see `references/headless-args.md`); with no `include`, step 3 takes the scope type's boundary default and names it in the envelope's `warnings` (a `specific-modules` recommendation that only the module count made becomes `full-library`), while a `reference-app` scope, or a `specific-modules` `scope_type` argument whose `intent` and `scope_hint` name no module, halts with `input-missing`; existing briefs are preserved unless `--force` was supplied (HALT with `overwrite-cancelled` otherwise); supplying `from_brief <path>` instead routes step 1 to the ratify path described in the `from_brief` Inputs cell (schema-validate, skip analyze/scope, write in place, no `--force` needed) rather than deriving a new brief |
| **Transient-failure retry** | This workflow does **not** auto-retry network or subprocess failures. A failed call the run can go on without (a doc URL that does not answer, a failed doc detection or QMD step, an extraction script that falls back to the prompt path) is logged, added to the run's warnings and reported in the result envelope's `warnings`, and the workflow continues with whatever signal it has; a failure it cannot go on without, such as step 2 unable to read the target, is a HARD HALT. Headless pipelines that want retry semantics should wrap the invocation at their orchestrator level (e.g. CI re-runner on non-zero exit). Rationale: brief-skill is read-mostly with one terminal write (the YAML at step 5); a partial-signal retry has more failure modes than just re-running the whole workflow, which is cheap. |
| **Exit codes** | See "Exit Codes" below |

## Exit Codes

Every HARD HALT in this workflow exits with a stable code so headless automators can branch on the failure class without grepping message text:

| Code | Meaning              | Raised by                                                                                  |
| ---- | -------------------- | ------------------------------------------------------------------------------------------ |
| 0    | success              | step 6 (terminal)                                                                         |
| 2    | input-missing / input-invalid | step 1 GATE: required headless arg absent (`target_repo`, `skill_name`, or `doc_urls` when `source_type=docs-only`) → `input-missing`; enum violation, malformed semver, non-kebab `skill_name`, or step 5 brief-context schema validation failure → `input-invalid`; a `scope_type=reference-app` argument with no `include` → `input-missing`. Step 3 §3: no `include` for a `reference-app` type the recommender picked, or for a `specific-modules` `scope_type` argument that names no module → `input-missing`. `[auto]` mode: step 1 §1b (no `brief_path` in the pipeline context), step 1a §1 and step 1b §1 (the brief is missing → `input-missing`, or fails the schema → `input-invalid`), step 1a §4 (the writer refuses the enriched brief → `input-invalid`) |
| 3    | resolution-failure   | step 1 §1 (`forge-tier.yaml` missing); step 2 §1 (target inaccessible / `gh auth` fails) |
| 4    | write-failure        | step 1 §1 pre-flight write probe (data folder or run folder unwritable: read-only mount, disk full, permissions denied); step 5 §3, or step 1a §4 in `[auto]` mode (write to `{forge_data_folder}/{skill-name}/skill-brief.yaml` failed) |
| 5    | overwrite-cancelled  | step 5 §2b (existing brief, `force` not supplied)                                         |
| 6    | user-cancelled       | any interactive menu in step 1/04 (user selected `[X]` Cancel and exit)                   |

## Result Contract (Headless)

This section is the one definition of the `SKF_BRIEF_RESULT_JSON` envelope. A run prints it when `{headless_mode}` is true, and in `[auto]` mode whatever `{headless_mode}` is:

- **Success**, once, on **stdout**: step 5 (write-brief.md §4b) after the brief is written, or step 1b (step-auto-validate.md §3) once an `[auto]` brief is written and checked.
- **Every HARD HALT that names a `halt_reason`**, on **stderr**, with `status: "error"`: SKILL.md's Halt Contract runs the emitter at the halt, in whatever step it fires.

```
SKF_BRIEF_RESULT_JSON: {"status":"success|error","brief_path":"…|null","skill_name":"…","version":"…|null","language":"…|null","scope_type":"…|null","exit_code":0,"halt_reason":null,"mode":"auto|null","warnings":["…"]}
```

`status` is `"success"` on the terminal happy path, `"error"` on any HALT. `halt_reason` is one of: `null` (success), `"input-missing"`, `"input-invalid"`, `"forge-tier-missing"`, `"target-inaccessible"`, `"gh-auth-failed"`, `"write-failed"`, `"overwrite-cancelled"`, `"user-cancelled"`. `exit_code` matches the table above; the emitter derives it from `halt_reason`. `skill_name` is `"unknown"` on a halt that fires before step 1 resolves the name. `mode` is `"auto"` in `[auto]` mode (pipeline auto-brief generation), `null` otherwise (interactive or headless-without-auto). `warnings` lists the run's warnings in the order they were raised, one string each (SKILL.md's `workflow_warnings[]`: the `warn:` lines steps log, the warnings helpers return, and each degraded signal the run went on past), a helper's `{field, message}` warning as one `<field>: <message>` line; it is left out when the run raised none. A failed `on_complete` hook is not in it: the hook runs after the envelope is printed, and the run displays the failure as a line of its own.

The shared emitter (`skf-emit-brief-result-envelope.py`) builds every line and checks it against `skf-brief-result-envelope.v1.json`, in the SKF module's `shared/scripts/schemas/`, so no step types an envelope.
