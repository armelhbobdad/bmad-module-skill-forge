# Source Access Protocol

## Source API Surface Definition

**Source API surface** = the package's top-level public exports. These are the symbols reachable from the primary entry point without importing internal modules:

- **Python:** symbols exported in the package root's `__init__.py` (including re-exports), excluding private (`_prefixed`) names. A sub-package behind a folder with no `__init__.py` (a FastAPI `routers/__init__.py`, say) is not a second package root when the folder of another package root that exports a name holds it, unless `scope.include` or `scope.tier_a_include` lists that `__init__.py`: its names stay out of the `all` and `root` sets (`excluded.nestedEntries`), while the `scope.include` and `tier_a_include` sets still count them and their signatures are still compared
- **TypeScript/JavaScript:** named exports from `index.ts` / `index.js` — exclude unexported locals
- **Go:** exported identifiers (capitalized) from the package's public-facing files
- **Rust:** items in `pub use` from `lib.rs` or `mod.rs`

The clauses below decide which part of that surface is the coverage denominator. Choosing the clause is a judgment, made here from the brief (`{forge_data_folder}/{skill_name}/skill-brief.yaml`), `{source_is_monorepo}` (coverage-check.md §0b) and the extraction; every count a clause names comes from `load-coverage-inputs.py` (coverage-check.md §2), in `surface.json`: the name `sets`, the `candidates` and the `guards`. The recipe runner already re-derives each barrel (multi-line re-export blocks, star re-exports and a Rust `pub use` chain included) and counts each name once, at the file that defines it, so a barrel that only re-exports adds nothing of its own. Without an extraction (Quick tier, the fallback per-file scan, States 2 to 4) the script builds the `scope.include` and `tier_a_include` sets from the files the names carry and the brief's globs, and there is no `subpaths` or `root` set (coverage-check.md §2b). Never re-count a barrel by hand.

- **Empty-barrel packages (copy-paste / subpath-only distribution):** the primary entry point is empty or re-exports nothing (`export {};`, an empty `__init__.py`, a `lib.rs` with no `pub use`). Do **not** compute coverage against the empty barrel: the denominator is the `scope.include` set, the union of named exports across the files the brief authorizes. The brief's `scope.notes` should say the distribution model is by design; when it does, treat the empty barrel as intended rather than a bug. With no brief and an empty barrel, set `analysis_confidence: docs-only` and report that the source API surface could not be determined.

- **Stratified-scope monorepo packages (curated subsets of multi-package repos):** `{source_is_monorepo}` is true AND the brief's `scope.include` lists a curated subset rather than the full workspace. The denominator reflects only the authored surface, not the monorepo's global export count. Resolution order:

  1. `stats.effective_denominator` (`candidates.statsEffectiveDenominator`) when `metadata.json` has it: the scalar branch, **subject to the deflation guard**. `effective_denominator` is a stored count, and a gap-driven `skf-update-skill` run can lower it, legitimately (a rescope expressed in the brief) or by gaming (dropping in-scope exports and setting it to the documented total). `guards.deflation` re-derives the surface from `scope.include` less `scope.exclude`, and when the brief carries no `scope.tier_a_include` (the only legitimate narrowing mechanism) and the re-derived source barrel exceeds `effective_denominator` by more than `guards.thresholds.deflationPct` percent, `guards.deflation.fires` is true and the `scope.include` set is the denominator instead, with a Medium `metadata-drift` gap (coverage-check.md §4). A legitimate scope reduction is expressed in the brief, through `scope.tier_a_include` or by adding the removed exports to `scope.exclude` (the mechanism `skf-update-skill` gap-driven rescope uses), never by editing `metadata.stats` to equal the documented count. With no surface read from the source (`guards.deflation.applicable` false), the guard does not run: annotate the report `effective_denominator used unverified: no source access to re-derive the barrel`.
  2. Otherwise the `tier_a_include` set when the brief has `scope.tier_a_include`, the narrow list of the surface the brief intends to document.
  3. Otherwise the `scope.include` set, **subject to the inflation guard**: `guards.inflation` compares it with the provenance-map entry count, and when `guards.inflation.fires` (above `guards.thresholds.inflationPct` percent) the coarse globs sweep in internal infrastructure the brief did not mean to document, a Medium `denominator-inflation` gap pointing at `scope.tier_a_include`. When `guards.umbrella.umbrella` is true (the root barrel is mostly re-exports), recommend `stats.effective_denominator` as the remediation instead.

  Leave `analysis_confidence` unchanged: stratified scope changes the denominator, not the confidence. Annotate the report: `Stratified scope, denominator: {effective_denominator | tier_a_include union | scope.include union} ({N} files matched, {M} exports union)`. `scope.notes` should document the stratification (for example "Tier A: fully documented; Tier B: deferred to references; Tier C: excluded"); when it does, treat the curated subset as intended, not a scope gap.

  **When this clause does not apply:** `scope.type: "full-library"` skills, single-package repositories, or stratified briefs where the full monorepo is intentionally in scope: use the standard barrel (the `all` set), **unless** the repo is a pattern-reference app or publishes a multi-subpath `exports` map. A `scope.include` glob that matches no file (a brief written for an older layout of the source) does not shrink that barrel: `guards.staleScope` restores the root exports defined in a file no glob covers, unless `scope.exclude` or a `scope-expansion` amendment whose latest action is `skipped` or `demoted-include` matches the file. The stale glob is a Medium `brief-scope-stale` gap (coverage-check.md §4).

- **Pattern-reference apps (non-library source):** a single-package repo that demonstrates an integration pattern rather than distributing a library API. Either trigger fires: `scope.notes` flags pattern-reference intent ("Reference app, not a library", "pattern-reference", "embedded-pattern skill", "skill value is the … pattern"; the author's words are authoritative), or the source has no barrel file at any recognized entry-point path (`__init__.py`, `index.ts`/`index.js`, `lib.rs`, `mod.rs`), `{source_is_monorepo}` is false and no multi-subpath `exports` map exists. The denominator is the `tier_a_include` set when the brief has one, else the canonicalized provenance map: build `surface.json` from the map alone, with coverage-check.md §2's State 2 command less its `--metadata` and with `--fold` (canonicalization, below), since `skf-create-skill`'s extraction already curated the map to the authored pattern surface. Leave `analysis_confidence` unchanged. Annotate: `Pattern-reference, denominator: {tier_a_include union | canonicalized provenance-map count} ({N} pattern surfaces)`. It does not apply to a repo with a non-empty barrel, a monorepo, or a `scope.type` of `specific-modules`, `public-api` with a multi-subpath `exports` map, `component-library`, `docs-only` or `reference-app` (whose brief carries its own pattern-surface denominator).

- **Single-crate curated subset (`scope.type: "specific-modules"`):** a single-package repo whose brief carves a subset of the crate's public surface with `scope.include` and `scope.exclude`. The denominator is the in-scope reachable barrel, the `scope.include` set (`stats.effective_denominator` first when present, under the same deflation guard). Annotate: `Specific-modules subset, denominator: in-scope reachable barrel ({N} items from {M} modules, after scope.include/exclude filtering)`. It does not apply to a monorepo, a `full-library` scope or an empty barrel.

- **Multi-entry (exports-map) packages:** an in-scope `package.json` declares an `exports` map with more than one non-root subpath and `{source_is_monorepo}` is false (`extraction.arms.multi_subpath_exports`), for `scope.type` `full-library` or `public-api`. Installers reach every published subpath, so the denominator is the `subpaths` set (wildcard subpaths are left out: their surface is unbounded), after the same ladder: `stats.effective_denominator` first (deflation guard), then the `tier_a_include` set. The root-barrel count (`candidates.rootBarrel`) is the secondary candidate in coverage-check.md §4's Denominator Candidates block. Annotate: `Multi-entry (exports-map), denominator: {effective_denominator | tier_a_include union | subpath union} ({N} subpaths resolved, {M} exports union; root barrel: {R})`. A root-only or wildcard-only map keeps the standard root barrel.

Internal module symbols are **excluded** from the coverage denominator unless they are explicitly documented in SKILL.md (in which case they count as documented extras, not missing coverage): the surface holds only the names the entry points export, and the extraction's `internal` names never reach it.

This matches the extraction-patterns.md convention used during skill creation: coverage measures how well SKILL.md documents what users actually import, not the entire internal codebase.

### Provenance-map canonicalization

A provenance map may hold **bookkeeping variants** of one export, artifacts of how the library structures its registry (Storybook's component-plus-story decomposition, accessibility renderer shadowing, exact-match renderer disambiguation). Counting them as separate exports inflates the denominator with names that are structural duplicates of a documented base export. When a clause takes its denominator from the provenance map, pass `--fold` to `surface`: it folds `X_def`, `X_exact` and `a11y_X` back to `X`, and `<prefix>X` back to `X` for each renderer prefix you pass as `--fold-prefix` (`mobile_`, `web_`, `ssr_`, only folded when `X` is an entry too), and reports the fold summary in `canonical.summary` for the report. This matches the convention `skf-create-skill` records in `metadata.json.stats.effective_denominator_source`: the base form is authoritative, the variant a sibling record.

Two judgments stay here:

- A variant the library's public surface genuinely distinguishes (an `a11y_Checkbox` documented and installed on its own) is a real export: pass it as `--keep`. Check SKILL.md for explicit documentation of the variant first; when in doubt, keep it and report both forms.
- When `stats.effective_denominator` is present and the raw entry count matches it, the map is already canonical: do not fold. When drift remains after folding (raw 222, canonical 215, `effective_denominator` 216), record the residual as an unexplained-reconciliation note; do not invent fold rules to close it.

## Source Access Resolution

Before analysis, determine source access level. Walk through these states in order — use the first that succeeds:

**State 1 — Local source available:**
Check if `{source_path}` (from metadata.json `source_root`) exists on disk. If yes → full analysis at detected tier (AST + signatures). Set `analysis_confidence: full`.

**State 2 — Local absent, provenance-map exists:**
Read `{forge_provenance_map}`, the provenance map init.md §2 bound (the skill version folder's, or the flat copy an older skill may still keep). When it is set and contains at least 1 entry, use it as the baseline export inventory. Each entry contains the structured fields `export_name`, `export_type`, `params[]`, `return_type`, `source_file`, `source_line`, `confidence`, and `ast_node_type`. Set `analysis_confidence: provenance-map`.

**Cross-reference with metadata.json:** the coverage denominator is the **union** of the provenance-map named exports and the `metadata.json` `exports[]` names, which `surface --provenance --metadata` (coverage-check.md §2) builds: an export in metadata but absent from the map counts as missing documentation, and the `state2` counts (`provenanceCount`, `metadataCount`, `unionCount`) go to step 5, whose scoring script decides whether the two disagree enough for the State 2 undercount deduction. When the union exceeds the map, report: "Provenance-map contains {provenanceCount} named exports but metadata.json lists {metadataCount} exports. Coverage denominator uses the union ({unionCount})." With no `metadata.json` `exports[]`, the map alone is the surface, with the note "Coverage denominator is provenance-map only: it may undercount if extraction was incomplete." If remote reading tools are available (zread, deepwiki, gh API, or similar), supplement by reading the entry point file for live signature verification.

**State 2 limitations:** Signature verification at State 2 is **string comparison only**, not semantic. Provenance-map stores parameters as flat string arrays (e.g., `["data: Union[BinaryIO, list, str]"]`), so `str` vs `String` or `list` vs `List[Any]` would be treated as mismatches even when semantically equivalent. For full type-aware verification (handling type aliases, generic equivalence), State 1 (local source) with AST re-parsing is required. When the SKILL.md was compiled from the same provenance-map (typical for create-then-test flows), most strings will match. However, enrichment (step 4) and doc-fetching (step 3c) during compilation may alter parameter descriptions, add type annotations, or normalize signatures, causing mismatches even in create-then-test flows. Expect some string-level mismatches and treat them as compilation artifacts, not source drift signals, until signature fidelity is enforced by step 5's Signature Fidelity Rule (see `signature_source` field in provenance-map entries).

**State 3 — No provenance-map, metadata exports exist (quick-skill path):**
If no provenance-map.json exists (typical for quick-skill output), fall back to `metadata.json`'s `exports[]` array for the export name list. Coverage check becomes a self-consistency comparison: are all names in `exports[]` documented in SKILL.md with description, parameters, and return type? Signatures cannot be verified. If remote reading tools are available, supplement by reading the entry point for live export comparison. Set `analysis_confidence: metadata-only`.

**State 4 — No local source, no forge-data, remote tools available:**
If neither provenance-map nor metadata exports provide a usable baseline, but remote reading tools (zread, deepwiki, gh API, or similar) are available and `source_repo` is set in metadata.json, read the entry point remotely to build the export inventory from scratch. Name-matching only — no AST. Set `analysis_confidence: remote-only`.

**State 5 — No source access at all:**
If none of the above succeed, fall through to docs-only mode (as defined in coverage-check.md Section 0: pre-analysis source type detection). Set `analysis_confidence: docs-only`. Warn: "**No source access available.** Coverage check evaluates documentation self-consistency only. Re-run with local clone or remote access for source-backed verification."

Set `analysis_confidence` in context for use in Section 2 analysis depth, step 5 output, and step 5 scoring. It names the source access only: tooling health is `toolingStatus`, which init.md records, and the two never overwrite each other.

**Confidence tier mapping:** `full` = T1, `provenance-map` = T1, `metadata-only` = T1-low, `remote-only` = T1-low, `docs-only` = T3. This aligns with the T1/T1-low/T2/T3 scale used across all SKF workflows.

**Degradation notice rules:** When `analysis_confidence` is `provenance-map`, check the `confidence` field of provenance-map entries before emitting a degradation recommendation:

- **All/most entries T1 (AST-verified):** The provenance-map data is already at highest confidence. Do not recommend re-running with a local clone — it would produce identical results. Use: "Resolved via: provenance-map (T1 AST-verified at compilation time). Local clone not required — provenance data is already at highest confidence."
- **Mixed T1/T1-low entries:** Report the breakdown. Recommend local clone only for the T1-low entries: "Resolved via: provenance-map ({n} T1, {m} T1-low). Re-run with local clone to upgrade T1-low entries to full AST verification."
- **All/most entries T1-low or lower:** Keep the standard recommendation: "Re-run with local clone for full AST-backed verification."
