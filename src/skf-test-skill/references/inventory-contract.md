# Documented Inventory Contract

The reader in coverage-check.md §1 reads only the files that section hands it: SKILL.md, the `references/*.md` files, `inventory-floor.json`, this contract and signature-comparison-rules.md. It never opens another run's folder under `_bmad-output/.skf-run/`, a test report, a `test-findings-*.json` ledger or a `skf-test-skill-result-*.json` file, so its inventory reads the skill alone. It runs no SKF script (coverage-check.md §1a runs `validate-inventory.py` on its response), reads no script's code, and writes or deletes no file but `{run_dir}/inventory-response.txt`: this contract and signature-comparison-rules.md alone decide its readings.

The contract `validate-inventory.py` checks (coverage-check.md §1a): each `kind` is one of `function`, `class`, `type`, `constant`, `hook`, `interface`, `method`, `struct`, `enum`, `trait`, `macro` or `adapter`; every entry carries the `description` the skill gives it (an empty string when it gives none); a function or method carries `params` (`""` or `[]` when it takes none; any list `params` holds the members of one parameter list, one per item, never one form per item) and `return_type` as the skill documents them, and leaves a key out when the skill documents nothing for it. An entry carries no key but `name`, `kind`, `description`, `params`, `return_type`, `usage_signature`, `signature_form`, `at`, `owner`, `methods`, `properties` and `fields`, and the validator refuses an inventory with any other, which no check reads (a `usage` written for `usage_signature` would leave its form uncompared). A name written with empty parentheses, or with only `...` or `…` between them, in running text or a description cell is a mention, not a form, whatever comes before the name (`await`, `new`, an assignment, a receiver or a module path): its entry leaves `params` and `usage_signature` out (a cell reading "`instrument()` wraps functions", a line reading "`await cognee.disconnect()` returns to local mode"), unless a return type follows its empty parentheses (`run_migrations() -> list[str]`), which makes it a signature, `params` `""` with that `return_type`. A description cell is any table cell but an export table's first cell and a cell whose column writes the call or signature, by its role (Signature, Props, Params, Parameters, Arguments, Usage, Syntax, Example and the like); a heading or an export table's first cell that writes `name()` is a form, recorded as written. A function's or a class's form the skill writes as a call expression of its own name (after `await`, `new` or an assignment, through a receiver or module path such as `coco.`, or as a statement in a fenced example; in running text or a description cell, only a call that passes an argument and writes no parameter type, `?`, bare `*` or `/`, with or without such a prefix, and no return type unless such a prefix comes before the name, such as `add(componentName, options)` or `await coco.mount(fn) -> Handle`), at a place `inventory-floor.json` gives no `signature` (below), is recorded whole in `usage_signature`, as `inventory-floor.json` writes a usage (an assignment, `await`, `new`, a receiver or module path before the name kept, through the call's closing parenthesis or the element's end, never an `@`, a `with` or text after the call), never in `params`, whatever names its arguments use, and a return type the skill writes for it in `return_type`, while a class's form written as a parameter list or a signature that is not such a call stays in `params` (`Note` above, written in a Signature cell): signature-comparison-rules.md reads a usage as a call and a list of bare names in `params` as parameter names. A call or JSX element of a name that a fenced example writes is not a place of its own when the skill also writes that name's form at a place that is no example (a heading, a table row, a props table, running text or a fenced declaration), unless the nearest heading above the example names a usage, its text holding the word usage whatever qualifies it (`## Usage`, `### Basic usage`, `### Usage pattern`; a bold label line such as `**Usage:**` is no heading): it gives no entry, so it is never compared, and a name whose only forms are in fenced examples keeps them. A `method`'s `name` is the bare method name and its `owner` the class or object it is called on (`agents` for `cognee.agents.get`, where the skill documents `agents` as a class; the class for one reached through a property, `client.messages`); `owner` is not validated. A function the skill documents in a module is a `function` named bare, never a `method`, even when it is called through the module's name (`register_sql_connection` for `cognee.tools.register_sql_connection`, where the skill documents `tools` as a module). Each `methods` item starts with the method's name, optionally after `async` (`async next_uuid(dep=None)`). A `const` holding a component (a `forwardRef`, `memo` or other wrapper call, or an alias like `const Tabs = TabsPrimitive.Root`) is a `constant` with the declaration or usage form the skill writes as `usage_signature`; a data constant carries no `usage_signature`, `params` or `return_type`. A name documented in several places is listed once per place, each entry with that place's form (`Card` above), and once per form at a place that writes several of its forms (two overloads in one row), each entry with that place as its `at`, never as one entry whose list `params` gives a form per item (the validator refuses a list of two or more items when one item holds several parameters or a whole form, or two items name the same parameter), and keeps one `kind` in every place. A form the skill marks as removed, or as the form of a version before the one it covers (a migration table's old-version column, a cell or row labelled gone, removed, before or old), is not a form of the current export and gives no entry, whether or not the covered version still exports the name, so it is never compared and records no gap: the current form beside it is that place's entry. A form marked only deprecated, and still present in the covered version, stays a form. Either way, a place `inventory-floor.json` gives the name still gives it an entry, removed or not, and a `signature` the floor gives there stays that place's form. An entry whose `params` or `usage_signature` the signature check compares (a list, a non-blank string, or a function's `params`, `""` included), except a `method`, gives that place as `at`, `"<path>:<line>"`: its file as the package names it (`SKILL.md`, or a file `references` lists) and the line its form starts on, the table row, the heading, the prose line or, in a fenced block, the line the declaration or call starts on (a `def` or `class` line, not a decorator above it), never a fence. That line writes the entry's `name`, or, in a fenced block, the block does. An entry with no compared form gives its place as `at` too, a `method` and a form that writes only a `return_type` (below) aside, so a gap about its name, such as a stale name's, cites that line. A place that writes a name but no form of it, and no `methods`, `properties` or `fields` its entry would carry (a mention, a bare code span, an import, a heading or prose that names or describes it), gives it no entry when another place gives the name one, unless `inventory-floor.json` gives that place; of several such places of a name no other place gives an entry, the first alone gives one: in SKILL.md, else the file that sorts first by path, at its lowest line. A comment in a fenced block is no place of its own and states no form or return type: a form or a return it writes (`// start: ({ options }: {...}) => Promise<void>`, `# returns the dataset's PipelineRunInfo`) is a note on the code, not a form of the name. The signature check compares a form with the declaration its own `[AST:]` or `[SRC:]` citations name, read at that place, when they name exactly one, at its line or below it, before the next declaration the surface records in its file (otherwise as it compares any form). For a name declared more than once, a place that writes two of its forms that differ (a row that documents one declaration's form and quotes another current declaration's form as a contrast) gives none of them a citation, so each is bound only by its other places; a form that writes only a `return_type` gives no `at`, so it is compared as one whose citations name no declaration. A missing or bad `at` (malformed, in another file, on a line that does not write the name, or not the place `inventory-floor.json` gives that form's `signature`) leaves its form unbound in the same way, and the validator lists it in its `warnings` instead of refusing the inventory. A place `inventory-floor.json` gives a `signature` (a cited function declaration, a Signature cell, a Props, Params or Parameters cell that is one code span, or a heading or an export table's first cell that writes one call; a usage form, such as `new Client(opts)`, in `usage_signature`; a Key params cell that opens with the row's name and its parameter group, on a row whose Kind cell names a function, method, class, generator or hook, such as `sync fn` or `abstract class`; a header with a Signature part, such as `Signature / Purpose` or `Props / Signature`, heads a Signature cell, while a `Props / Usage` or `Props / Type` cell and an Arguments, Args, Usage, Syntax or Example cell are none of these, so their forms stay the reader's) has that form as its entry, with that place as its `at`, whatever its kind, its non-blank fields kept as given (a `params` or `usage_signature` may open with the shared text the next sentence gives, then `; `, and a `params` may spell the shared members out before, among or after its own, in the order the skill gives); a blank one is the reader's, left out when the place writes none, and a form the skill writes only in prose is an entry of its own; a `signature` read from a cell under a partial label (`Signature (simplified)`, `Props (simplified)`, `(partial)`, `(key parameters)`) or from a Key params cell, or whose parameter group holds a `...` or `…` that is a member of its own, standing in for omitted members (not one inside a nested type, object or element), also gives `signature_form` `"partial"`, which that entry copies, and the validator refuses an inventory with no entry there that does. The label at a place `inventory-floor.json` gives a `signature` is the `signature`'s: an entry that gives its form there or with no `at` gives `"partial"` only when the `signature` does, and the validator refuses one that adds it (a skill labels such a form partial in its column header, not in words), while another form the place writes keeps its own label (a second overload in the row whose own `...` labels it partial). Where the skill documents several names and states members they share once, in the same place (a table row, a paragraph) or over a table for all its rows (a sentence or caption just above it, or its column header), each name's entry carries that shared text in its `params` (in its `usage_signature`, for a usage form), never in a `methods` item, which still starts with the method's name: the shared text first, then `; `, then the name's own members as the skill writes them, without the name, never the name's own members alone (`Note` above, from a row that documents `Note` and `Task`, each with the base fields `id, scope=Scope()`, as `Note(content, title=None)` and `Task(title, done=False)`). A name such a place lists bare, with no parameter list, call or signature of its own there (`.get` in a namespace row that lists `.create`, `.get` and `.delete`, each with an optional `user`, and links to their signatures), is a mention at that place: its entry leaves `params`, `return_type` and `usage_signature` out, and the shared text applies only to names the place gives members of their own; a whole parameter list, call or signature the place writes once for every name it lists (the Signature cell of a row whose first cell lists `get` and `head`) is no shared text but each of those names' own form there, recorded as written. When the skill places one of the name's own members before or among the shared ones (`leading`, `first`), the entry writes the name's whole list in the order the skill gives instead, the shared members spelled out and no `; `, unless `inventory-floor.json` gives that place a usage form, whose `usage_signature` then stays after the shared text and `; `. An entry whose signature the skill labels partial (simplified, key parameters, a `...` standing in for omitted members, not rest or variadic syntax; a label in a table's column header, such as `Props (simplified)`, labels each of its rows) carries `signature_form: "partial"`, any other `"full"` or no key: copy the label, never judge the form. A table that documents one export's props, a row per prop with its type (Create Skill's `| Prop | Type | Default | Description |`, or one with a Required column), is a place of its own: its entry, whatever its kind, gives as `at` the nearest heading or caption above the table that writes the name (a row writes a prop, not the name, and a call or JSX element of the name a row's cell writes is an example of that prop, never a place of its own) and as `params` one object type of the rows in row order, `{ prop: Type; ... }`, `prop` alone for an empty Type cell and each `\|` read as `|`, with no default, `?` or Required mark, so it states no optionality (signature-comparison-rules.md compares it as a typed props list); a partial label in its column header still labels it partial. A table that documents one function's, method's or class constructor's parameters, a row per parameter with its type (`| Param | Type | Default | Description |`, or one with a Required column), is a place of its own too: its entry, whatever its kind, gives as `at` the nearest heading or caption above the table that writes the name (a row writes a parameter, not the name) and as `params` one parameter list of the rows in row order, `param: Type, ...`, `param` alone for an empty Type cell and each `\|` read as `|`, with no default, `?` or Required mark, so it states no optionality (signature-comparison-rules.md reads it as a typed parameter list); a partial label in its column header, its caption or the nearest heading above it (`### Key parameters`) labels it partial; when that heading or caption writes a form of the name itself (`### connect(host: str, port: int = 5432)`), the table adds no entry there, so that place keeps one form and its citations still bind it.

A name the skill writes only in a type position (a parameter type, a return type or a type argument inside another entry's documented type or signature, or a parameter table's Type cell) is a type mention, not an export the skill documents, even when its code span is exactly the name, and gets no entry, unless the skill also writes it as one outside a type position: a place `inventory-floor.json` gives it, a heading, an export table's first cell, a code span that is the name or the name then `(`, or a fenced declaration. A name the skill presents only as a local import alias of another name, or says the source does not export, is not an export the skill documents either: it gets an entry only from a place `inventory-floor.json` gives it, a heading, an export table's first cell or a fenced declaration of it (an import is not one), never from a code span in prose or a description cell. A sentence saying the skill does not cover a name ("out of scope for this skill", "not covered here") does not document it and gives it no entry, whatever form it writes the name in; any other place that documents the name (a form, prose or a description cell that calls or describes it, or a place `inventory-floor.json` gives it) still gives it one. A `const` whose value is a function (annotated with a function type, bound to an arrow, a `function` or a call that returns one, or written with a parameter list) carries the function form the skill writes for it as `params` (`[]`, never `""`, when it takes none) and `return_type`, whatever its kind (`constant` for the skill's `const` label), wherever the skill writes it, a description cell included, except a call expression of its name, which is recorded in `usage_signature` as a function's is (above); a bare `name()` there is still a mention; only a constant holding neither a component nor a function is a data constant. A `const` holding a function, not a component, that a place writes only as the call that builds it (`const badgeVariants = cva(…)`), with no parameter list, function type or return type of its own, carries no `params`, `return_type` or `usage_signature` there: that call is the factory's form, not the const's. A function or class an example defines is the reader's own code, not a form of a same-named export, only at a place `inventory-floor.json` gives no `signature` and only when its fenced block also defines names the skill does not document as exports or, whatever else the block defines, decorates the definition with, passes it to or registers it through that export itself, by its name or through a receiver or module path (`@coco.lifespan` over `async def lifespan(builder: coco.EnvironmentBuilder):`), never through an attribute of it such as `@x.setter`: its entry there leaves `params`, `return_type` and `usage_signature` out, as a mention's does, so it is never compared and records no gap; a declaration the floor gives a `signature` stays that place's form.

A `cross_check_mismatches` entry gives its `export`, `reference_file`, `reference_line` and an `issue` that names each form by its file's path, and the pair's other side: the SKILL.md body's line as `skill_md_line`, or, for two references, the one that sorts first in codepoint order, by path and then line, as `other_file` and `other_line`, with the one that sorts last as `reference_file` and `reference_line`. Each file is its path in the package, such as `references/api-reference.md`. A pair of a `method`'s forms also gives the `owner` its entries give (`agents` above), so the split-body Source reads that owner's member, never a same-named declaration elsewhere; `owner` is not validated. Methods of one name whose entries give different owners (`agents.get`, `datasets.get`) are two methods, and their forms are never a pair.

A mismatch's `export` is the `name` of an inventory entry, a `method`'s bare `name`. `validate-inventory.py` refuses an inventory with a mismatch whose `export` names no entry by its `name` or, for a `method` that gives an `owner`, by `{owner}.{name}`: an empty string, a number or a name no entry has would title a split-body gap with an export the inventory does not list.

`undecided` lists each reading this contract or signature-comparison-rules.md leaves open that the inventory rests on: a place whose shape no sentence settles, or that two sentences settle differently, so another reader could give it another entry, form or label, or another `cross_check_mismatches` entry. Each item gives the `export` it concerns, its place as `at` (as an entry gives it; null when it has none), the `rule` that leaves it open (the sentence, quoted), the `reading` taken and, as `other_gap`, what the other reading would give (a Critical `signature-mismatch`, a split-body mismatch, or no gap). An empty list or no key says the rules left no reading open. `validate-inventory.py` drops, with a warning, an item that is no object, leaves `export`, `rule`, `reading` or `other_gap` blank or gives a blank `at`, never refusing the inventory for it, and keeps the rest of the list in the inventory it writes, and coverage-check.md §5's render lists each item under Borderline Calls, so the report names each reading its verdict rests on. It changes no entry or gap.

`validate-inventory.py` adds `crossChecked` to the inventory it writes, `{"count": <int>, "names": [<name>, ...]}`: each inventory name, once, that two or more of the files it reads write (SKILL.md and each file `references` lists), by the spot-check's name match outside `[AST:]`, `[SRC:]` and `[EXT:]` citations, so a mention in prose counts. The reader writes no `crossChecked`; the validator replaces one it finds.
